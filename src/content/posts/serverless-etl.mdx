<h2 id="ingestion-boundary-and-event-flow">Part 1: What problem does this solve?</h2>

### The problem

A common problem for most teams who manage large datasets is: how do you reliably ingest files from S3 into 
a queryable format? The solution needs to be timely, cost-effective, and observable. In an AWS environment, 
we need a system that can respond to new data sets in S3, transform them into a structured format, and store them 
in a way that allows for other services like Athena to query them. 

<br/>

In order for it to be timely, the solution needs to be event-driven, so that it can respond to new data as it is uploaded. In order for it to be cost-effective, 
the solution needs to be serverless, so that it can scale up and down as needed without incurring unnecessary costs. 
Finally, in order for it to be observable, the orchestration layer needs to provide visibility into the data ingestion 
process and any errors that may occur so that they can be diagnosed and resolved quickly.

### The solution

There are 3 layers to this solution architecture:
  - Storage
  - Orchestration
  - Compute

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

For storage, we have to consider locations for both the incoming source data feed and the transformed data. The transformed data
will be referenced by downstream services and analytics teams. For this reason, we will use a common and highly optimized data store, 
Apache Iceberg tables. In this architecture, the source data is stored in a general S3 bucket, while the transformed data is stored 
in AWS managed Iceberg tables using S3 Table Buckets. This allows for a clear separation of concerns between the raw data and the 
transformed data.

We want to give the incoming data feed a clear location in the S3 bucket, so we will make sure that data is uploaded with a prefix 
`feed/`. This allows us to easily identify objects as new data to be ingested.

<StorageDiagram />

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

The orchestration layer is responsible for coordinating the ingestion process. The first step is to detect when new `feed/` objects
are created. Luckily, the S3 bucket can be configured to send events to EventBridge. Using an EventBridge rule, we can filter for 
the `feed/` prefix and trigger whichever downstream process we want.

In an AWS environment, I'm a huge fan of the Step Functions service for running multi-step workflows. It provides a visual representation
of the workflow, built-in error handling, and the ability to run parallel tasks. This checks off the boxes for timeliness, cost-effectiveness, 
and observability. The Step Functions state machine will be triggered by the EventBridge rule.

<OrchestrationDiagram />

<div className="architecture-layer-heading">
  <span>03</span>
  <h4>Compute</h4>
</div>

Now that we have a way to detect new data and orchestrate the ingestion process, we need a compute layer to actually perform the 
transformation. I have found that EMR Serverless and Spark is a great option for this. EMR Serverless gives us direct control over the
Spark session configuration. This is important because we need to configure an Iceberg REST catalog that connects to our S3 Table Bucket
through the AWS Glue Iceberg REST endpoint. The S3 Tables integration exposes the bucket through Glue's federated `s3tablescatalog`,
allowing Spark to read from and write to the Iceberg tables.

Outside of transforming the data, there is an opportunity to capture runtime statistics. This 
adds to the observability of the ETL pipeline and allows for downstream consumers to react. For example, we can capture the number
of rows in the source parquet file, averages of certain columns, or any other custom metrics. Downstream services can use this 
information to trigger notifications or alert on anomalies. For this solution, the job will write the stats as a JSON file to a separate 
location in the source data S3 bucket, such as `runs/<execution-id>/stats/`. This way we can easily correlate the stats with the 
specific execution of the state machine, and the relevant source data is also in the same bucket.

Normally in step functions that run these long-running jobs, I like to use a Lambda function to validate the input data according to a
JSON schema and prepare the input for downstream tasks. The user experience is nicer because it means that we can fail faster and cheaper 
if the input is malformed or if the file doesn't exist (maybe the file was deleted before the state machine started), and the EMR job can
just focus on the transformation.

<h2 id="infrastructure-as-code">Part 2: Infrastructure as code — the SAM template</h2>

The entire stack is defined in a single `template.yaml` using the AWS SAM
transform. This section walks through what gets deployed and why.

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Security foundations</h4>
</div>

- **KMS key with auto-rotation** — Customer-managed encryption for all data at rest; bucket-key enabled to reduce API costs.
- **S3 Bucket policy** — Denies non-SSL traffic; scopes access to the AWS Organization via `aws:PrincipalOrgID`.
- **Versioning + lifecycle** — 30-day non-current version expiry balances recovery with storage costs.
- **Access logging** — Logs to a separate bucket with a stack-specific prefix.
- **IAM: least-privilege per service** — Separate roles per actor, ARNs scoped as tightly as possible.
- **LakeFormation enabled** — Row/column-level access control on Glue Catalog resources.

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Storage</h4>
</div>

### KMS Key Encryption

A customer-managed KMS key encrypts every object in the data bucket. Auto-rotation is
enabled and the bucket uses S3 Bucket Key to reduce per-request KMS calls.

```yaml
EncryptionKey:
  Type: AWS::KMS::Key
  Properties:
    Description: KMS key for S3 Bucket
    EnableKeyRotation: true
```

### DataBucket

The data bucket is the landing zone for source files and run artifacts. EventBridge
notifications are enabled so downstream rules can react to `feed/` uploads. Versioning,
public access blocks, logging, and lifecycle rules are all configured inline.

```yaml
DataBucket:
  Type: AWS::S3::Bucket
  Properties:
    NotificationConfiguration:
      EventBridgeConfiguration:
        EventBridgeEnabled: true
    BucketEncryption:
      ServerSideEncryptionConfiguration:
        - ServerSideEncryptionByDefault:
            SSEAlgorithm: aws:kms
            KMSMasterKeyID: !GetAtt EncryptionKey.Arn
          BucketKeyEnabled: true
    VersioningConfiguration:
      Status: Enabled
    PublicAccessBlockConfiguration:
      BlockPublicAcls: true
      BlockPublicPolicy: true
      IgnorePublicAcls: true
      RestrictPublicBuckets: true
    LoggingConfiguration:
      DestinationBucketName: !Ref LoggingBucketName
      LogFilePrefix: !Sub "${AWS::StackName}/"
    LifecycleConfiguration:
      Rules:
        - Id: ExpireNonCurrentVersions
          Status: Enabled
          NoncurrentVersionExpiration:
            NoncurrentDays: 30
```

The bucket policy denies insecure transport and scopes access to the organization:

```yaml
BucketPolicy:
  Type: AWS::S3::BucketPolicy
  Properties:
    Bucket: !Ref DataBucket
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: DenyInsecureTransport
          Effect: Deny
          Principal: "*"
          Action: "s3:*"
          Resource:
            - !GetAtt DataBucket.Arn
            - !Sub "${DataBucket.Arn}/*"
          Condition:
            Bool:
              aws:SecureTransport: "false"
        - Sid: AllowOrganizationAccess
          Effect: Allow
          Principal:
            AWS: "*"
          Action:
            - s3:GetObject
            - s3:PutObject
            - s3:DeleteObject
            - s3:ListBucket
            - s3:GetBucketLocation
          Resource:
            - !GetAtt DataBucket.Arn
            - !Sub "${DataBucket.Arn}/*"
          Condition:
            StringEquals:
              aws:PrincipalOrgID: !Ref PrincipalOrgId
```

### S3 Tables Resources

Three CloudFormation resources define the S3 Table Bucket destination. We define the 
  - Table Bucket
  - The Namespace which is similar to a Glue Database
  - The table which matches Glue Table

I chose to declare the table in the template to make this service simple. It also means it exists before 
the first pipeline run, so there is no "create table if notexists" logic in Spark.

```yaml
IcebergTableBucket:
  Type: AWS::S3Tables::TableBucket
  Properties:
    TableBucketName: !Ref TableBucketName

IcebergDefaultNamespace:
  Type: AWS::S3Tables::Namespace
  Properties:
    TableBucketARN: !GetAtt IcebergTableBucket.TableBucketARN
    Namespace: default

# test table for this service with a simple schema
IcebergTestDataTable:
  Type: AWS::S3Tables::Table
  DependsOn: IcebergDefaultNamespace
  Properties:
    TableBucketARN: !GetAtt IcebergTableBucket.TableBucketARN
    Namespace: default
    TableName: test_data
    OpenTableFormat: ICEBERG
    IcebergMetadata:
      IcebergSchema:
        SchemaFieldList:
          - Name: id
            Type: long
            Required: true
          - Name: name
            Type: string
            Required: false
          - Name: amount
            Type: double
            Required: false
```

  <h4>Compute</h4>

### EMR Serverless App

A Spark application on EMR release 7.8.0 (ARM64). Auto-start and auto-stop with a
2-minute idle timeout means zero cost when the pipeline isn't running.

```yaml
EmrApp:
  Type: AWS::EMRServerless::Application
  Properties:
    ReleaseLabel: emr-7.8.0
    Architecture: ARM64
    Type: Spark
    AutoStartConfiguration:
      Enabled: true
    AutoStopConfiguration:
      Enabled: true
      IdleTimeoutMinutes: 2
```

#### PySpark script highlights

The `load_data.py` script is intentionally minimal: read Parquet, write to Iceberg
via `INSERT OVERWRITE`, and emit a stats JSON for the orchestrator. Catalog configuration
lives entirely in `SparkSubmitParameters`, keeping the script portable.

```python
def main(input_path, catalog_id, namespace, table_name, stats_s3_uri=""):
    iceberg_table = f"s3tablesbucket.{namespace}.{table_name}"

    spark = (
        SparkSession.builder
        .appName(f"S3TableBucket-Import-{table_name}")
        .getOrCreate()
    )

    df = spark.read.parquet(input_path)
    count = df.count()

    df.createOrReplaceTempView("source_data")
    spark.sql(f"INSERT OVERWRITE {iceberg_table} SELECT * FROM source_data")

    if stats_s3_uri:
        _write_stats_file(stats_s3_uri, input_path, catalog_id,
                          namespace, table_name, count)
    spark.stop()
    return 0
```

The stats file written to `runs/<execution-id>/stats/<table>.json` is read back by
the state machine so structured metadata flows downstream without parsing Spark logs.

### Validate Input Lambda

A sub-second Lambda that fails the execution fast and cheap before EMR provisioning.
It validates the EventBridge payload against a JSON Schema and resolves which Iceberg
table to target using regex patterns from `file_mapping.json`.

```yaml
ValidateInputFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: validate_input.handler
    CodeUri: lambda/validate_input/
```

#### Handler highlights

```python
@logger.inject_lambda_context
def handler(event, context):
    validate(event=event, schema=INPUT_SCHEMA)

    for mapping in event["SourceFileTableNameMapping"]:
        if "TableName" not in mapping:
            table_name = resolve_table_name(
                mapping["SourceFile"], FILE_PATTERN_MAPPINGS
            )
            mapping["TableName"] = table_name

    return event
```

Table resolution matches the S3 key against regex patterns sorted by specificity
(longest first). Adding a new ingestion target requires only a new entry in
`file_mapping.json` and a corresponding table resource in the SAM template.

```json
{
  "mappings": [
    {"tableName": "test_data", "filePattern": ".*/test-data\\.parquet$"}
  ]
}
```

### State Machine

The state machine uses JSONata (not JSONPath) for data transformations and the
`.sync` integration pattern so Step Functions polls EMR until completion — no custom
polling loop needed.

#### ASL highlights

The Map state iterates over resolved table mappings. Each iteration runs the full
EMR → stats → emit pipeline independently. Per-item `Catch` blocks route failures
to a "Fail Item" pass state so one table's failure doesn't abort others.

```json
"Load Tables": {
  "Type": "Map",
  "Items": "{% $states.input.SourceFileTableNameMapping %}",
  "ItemProcessor": {
    "ProcessorConfig": { "Mode": "INLINE" },
    "StartAt": "Load Data",
    "States": {
      "Load Data": {
        "Type": "Task",
        "Resource": "arn:aws:states:::emr-serverless:startJobRun.sync",
        "Retry": [{
          "ErrorEquals": [
            "EmrServerless.EmrServerlessException",
            "EMRServerless.AWSEMRServerlessException",
            "EMRServerless.ValidationException"
          ],
          "IntervalSeconds": 15,
          "MaxAttempts": 10,
          "BackoffRate": 2
        }],
        "Catch": [{
          "ErrorEquals": ["States.ALL"],
          "Next": "Fail Item"
        }],
        "Next": "Get Stats Object"
      }
    }
  }
}
```

After the Map completes, a Choice state counts failed items — if any table has
`status: "failed"`, the execution fails. This makes partial success visible in the
Step Functions console.

```json
"Check Table Results": {
  "Type": "Choice",
  "Choices": [{
    "Condition": "{% $count($states.input[status = 'failed']) > 0 %}",
    "Next": "Fail"
  }],
  "Default": "Succeed"
}
```

### Event Rule and Input Transformer

An EventBridge rule filters for `Object Created` events under the `feed/` prefix
and invokes the state machine via an `InputTransformer` that extracts the S3 key
into the expected payload shape.

```yaml
FeedUploadRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source:
        - aws.s3
      detail-type:
        - Object Created
      detail:
        bucket:
          name:
            - !Ref DataBucket
        object:
          key:
            - prefix: "feed/"
    Targets:
      - Id: LoadDataStateMachine
        Arn: !GetAtt StateMachine.Arn
        RoleArn: !GetAtt EventBridgeStateMachineRole.Arn
        InputTransformer:
          InputPathsMap:
            key: $.detail.object.key
          InputTemplate: |
            {
              "SourceFileTableNameMapping": [{"SourceFile": "<key>"}],
              "Event": {"source": "aws.s3", "detail-type": "Object Created", "key": "<key>"}
            }
```

The `EventBridgeStateMachineRole` has a single permission — `states:StartExecution`
scoped to the state machine ARN.

<div className="architecture-layer-heading">

Build and deploy are standard SAM. A `post-deploy.sh` script handles uploading the
PySpark entrypoint to S3 and applying Lake Formation grants that CloudFormation can't
express natively.

```bash
sam build && sam deploy
./scripts/post-deploy.sh
```

The post-deploy script is idempotent — safe to re-run on every deploy:

```bash
# Upload PySpark entrypoint
aws s3 cp emr/load_data.py "s3://${DATA_BUCKET}/emr/load_data.py"

# Apply Lake Formation grants (catalog → database → table)
aws lakeformation grant-permissions \
  --principal "DataLakePrincipalIdentifier=${EMR_ROLE_ARN}" \
  --resource '{"Catalog":{"Id":"<catalog-id>"}}' \
  --permissions '["CREATE_DATABASE", "DESCRIBE"]'
```

For context, Step Functions provides 4,000 free state transitions per month and Lambda
includes 1M requests + 400,000 GB-seconds free — so for light development and testing,
those services are literally $0.

### Cost attribution

The stack is tagged with an application identifier, which means all resources created by
CloudFormation inherit the tag. This integrates with AWS Cost Explorer, AWS Budgets, and
Cost Allocation Tags to track spend per pipeline — useful when you're running multiple
workloads in the same account and want to attribute costs back to individual services or
teams.

<h2 id="tradeoffs-and-next-steps">Part 4: Production considerations and future additions</h2>

### Production considerations

- **INSERT OVERWRITE, not MERGE** — The current job does a full overwrite. For append-only feeds this is fine; for update-heavy data you'd want an upsert/merge strategy with a deduplication key.
- **Single-file-per-event granularity** — Each file triggers a full execution. For high-frequency small files, a micro-batching strategy (SQS buffer + scheduled trigger) would reduce per-file overhead.
- **No dead-letter queue** — Failed events currently surface only in Step Functions execution history. A DLQ on the EventBridge target would make unprocessable events more discoverable.
- **S3 Bucket Deletion Policy** — Set the DeletionPolicy of the S3 buckets to Retain in production so data is not lost when the stack is deleted.
- **Extending to multiple tables** — Adding a new ingestion target requires only a regex pattern in `file_mapping.json` and an `AWS::S3Tables::Table` resource in the SAM template. No changes to the state machine, Lambda code, or PySpark script — the architecture is table-count-agnostic by design.

### Future additions

- Schema evolution handling — detect new columns in Parquet and evolve the Iceberg schema
- Data quality checks (Great Expectations or Deequ) as a pre-write gate
- Multi-account deployment via AWS Organizations + StackSets
