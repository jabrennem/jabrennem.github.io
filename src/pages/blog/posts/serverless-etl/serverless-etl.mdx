This project shows how I approach a data engineering architecture for a real, slightly awkward
workload: an external team drops a batch of small Parquet files with hundreds to thousands of rows into S3 every 
day. Every so often the files are very large with hundreds of millions of rows. I need to load the files into
Apache Iceberg tables without keeping compute running between uploads — and without spinning up more jobs 
(or more cost) than the batch actually warrants.

I start with the requirements, explain how they shaped the storage, orchestration, and compute layers — and the
reasoning behind each decision — with a short note on how it's built. Then I run it end to end, look at whether
the batching actually saved money, and finish with the current tradeoffs and the improvement I'd reach for next
if the volume grew.

<h2 id="problem-and-solution">Part 1: Problem and solution</h2>

### The problem

An external team uploads a batch of Parquet files to S3 most days — roughly 8 to 10 at a time, a few hundred
records each. They usually arrive together, but can also be delayed by hours. Each file is destined for one of a
couple of Iceberg tables in our catalog. Every once in a while that same team sends a much larger file, with
hundreds of millions of records.

I'm on a small team, so the design has to require the least amount of resource management possible: when
something goes wrong I want to diagnose it and get the data ingested again as quickly as possible. Cost is a
priority too — the files are usually small, so I don't want to pay for a heavyweight job (or several) to move a
few kilobytes.

That shapes four requirements. The pipeline should consolidate a day's uploads into one run instead of reacting
to each file, scale to zero between batches, spend compute in proportion to the data, and log enough history to
trace a failure and safely re-run it.

### The solution

I split the solution into three layers so each concern can be designed and operated
independently:

- Storage
- Orchestration
- Compute

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

This architecture separates storage for the incoming data feed and the Iceberg table data referenced by
downstream services and analytics teams. I store the source data in a general S3 bucket and use an S3 Table
Bucket for the AWS-managed Iceberg tables — a clear boundary between raw data and catalog data. Incoming files
land under the `feed/` prefix, which gives the pipeline a single place to watch, and each file resolves by name
to one of two Iceberg tables (`test_data` and `customers`).

<StorageDiagram />

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

The orchestration layer decides *when* to run and consolidates a window of uploads into a single execution.
The obstacle is that reacting to each S3 event — with an EventBridge target, a Pipe, or an SQS-to-Lambda
source — fans a batch of files out into several executions, because those integrations poll in parallel and
flush eagerly. That would defeat the whole point of batching. So I decouple arrival from processing: S3 sends
`Object Created` events for the `feed/` prefix to EventBridge, which drops them into an SQS queue that simply
buffers the day's uploads. On a timer, EventBridge Scheduler invokes a Message Poller Lambda that drains the
queue and, if anything is waiting, starts exactly one Step Functions execution with the whole file list. A
timer is the one trigger that deterministically turns a window of arrivals into a single run. Step Functions
then gives me a visual execution history, built-in error handling, and parallel task support — and every piece
here is managed, so the layer scales itself.

<OrchestrationDiagram />

<div className="architecture-layer-heading">
  <span>03</span>
  <h4>Compute</h4>
</div>

The compute layer loads the batch into Iceberg while spending as little on EMR as the data allows. EMR
Serverless is the expensive part, and it charges a per-job floor whether a job moves a few kilobytes or
gigabytes. So the real decision is *how to pack files into jobs*.

A Lambda runs first: it validates the payload, resolves each file to its table by filename, and bin-packs by
size. Every file over a threshold gets its own job; all the small files share one. A Step Functions Map state
then runs one EMR Serverless Spark job per group — and a single job can write to several tables at once.

Loads are idempotent by design. Each row carries its source S3 URI in a `source_file` column, and before
appending a file the job checks whether that URI is already in the table — so re-running a failed execution
never double-loads. (I first tried `MERGE`, but it hit a Lake Formation 403 on S3 Tables; a plain
check-then-append uses only the operations that work.)

If any group fails, a Choice state fails the whole execution — keeping the completed loads and surfacing the
failure in the console. Each job also drops a per-group stats JSON under `runs/<execution-id>/stats/` for
downstream use, so nobody has to parse Spark logs.

<ComputeDiagram />

### How it's built

The whole thing is one AWS SAM application — an S3 bucket, an SQS queue, an EventBridge rule and Scheduler, two
small Lambdas (the Message Poller and the Validate/bin-pack function), a Step Functions state machine, an EMR
Serverless Spark application, and an S3 Table Bucket with the two Iceberg tables (`test_data` and `customers`).
Keeping it in one template means the destinations and their schema exist before the first run and every change is
reviewable in a pull request. I'm not walking through the YAML here — it drifts, and the diagrams above already
show how the pieces fit — so the [full source is on GitHub](https://github.com/jabrennem/serverless-etl-s3-tables)
if you want to read it.

<h2 id="demo-and-results">Part 2: Demo and Results</h2>

To exercise the architecture I deploy the stack, generate a batch of test files across both tables, and upload
the whole folder at once. Then I follow the single Step Functions execution as it fans out into one EMR job per

### Configure the deployment

Before deploying, I add the AWS Organization ID and the existing access logging bucket to the `parameter_overrides`
in `samconfig.yaml`:

```yaml
parameter_overrides:
  - PrincipalOrgId=o-xxxxxxxxxx      # your AWS Organization ID
  - LoggingBucketName=my-logging-bucket  # existing S3 bucket for access logs
```

### Build and deploy

With those values set, I specify an AWS profile and run the standard SAM build and deploy commands:

```bash
export AWS_PROFILE=profile_name
sam build
sam deploy
```

I run `sam build` to package the Lambda function and produce the transformed template used
for the deployment. This output is the first checkpoint that the application code and template 
built successfully.

### Prepare the test batch

`scripts/generate_test_data.py` writes a folder of small Parquet files split across both tables, with a couple
of deliberately larger files mixed in so the size threshold has something to isolate. The `test_data` files
carry `id`, `name`, and `amount`; the `customers` files carry `customer_id`, `email`, and `region`.

```bash
python scripts/generate_test_data.py --out test-batch --count 10
```

### Trigger the workflow

`trigger.sh` uploads the whole folder to the `feed/` prefix. Each object lands in the SQS queue; on its next
tick the scheduled Message Poller drains the queue and starts **one** state machine execution for the batch.

```bash
./scripts/trigger.sh test-batch
# Uploads every *.parquet under test-batch/ to s3://<bucket>/feed/
```

of jobs — the small files packed together, each large file on its own.

### Reruns are safe

To prove the idempotency claim, I re-ran the same execution. The loader reads each file but skips the append
when that `source_file` is already in the table — so the second run committed nothing. Here's the driver log
from the batched small-file job on the rerun:

```text
Batch of 8 file(s) into catalog <ACCOUNT_ID>:s3tablescatalog/serverless-etl-table-bucket
Loading .../feed/customers-01-...-29403.parquet into s3tablesbucket.default.customers
  read 165 records
  skip .../feed/customers-01-...-29403.parquet -- already loaded into 's3tablesbucket.default.customers'
Loading .../feed/test-data-04-...-29834.parquet into s3tablesbucket.default.test_data
  read 145 records
  skip .../feed/test-data-04-...-29834.parquet -- already loaded into 's3tablesbucket.default.test_data'
  ... (all 8 files skipped)
```

All eight files skipped; the table row counts were unchanged. That's the whole safety net for a small team —
if a run half-fails, you just run it again.

### Did grouping actually save money?

The batch is 10 files (8 small, 2 big) run as **3 EMR jobs**. The billed resource use per job, from the EMR
console:

  <thead>
    <tr>
      <th>Job</th>
      <th>Files</th>

      <th>Billed memoryGB-hours</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Group 1 (small, batched)</td>
      <td>8</td>
      <td>0.287</td>
      <td>1.147</td>
    </tr>
    <tr>
      <td>Group 2 (big)</td>
      <td>1</td>
      <td>0.267</td>
      <td>1.067</td>
    </tr>
    <tr>
      <td>Group 3 (big)</td>
      <td>1</td>
      <td>0.267</td>
      <td>1.067</td>
    </tr>
    <tr>
      <td><strong>Grouped total</strong></td>
      <td>10</td>
      <td><strong>0.821</strong></td>
      <td><strong>3.281</strong></td>
    </tr>
  </tbody>
</table>

Every job billed about the same (~0.27 vCPU-hours) no matter what it loaded — that's the EMR Serverless per-job
floor. Running the 8 small files as separate jobs would pay that floor 8 more times: ~2.67 vCPU-hours vs 0.821
grouped, roughly **3× less billed compute** for the same data. And between batches the app auto-stops after two
idle minutes, so there's no idle compute at all.

<h2 id="tradeoffs-and-next-steps">Part 3: Tradeoffs and next steps</h2>

Already handled: size-based grouping so EMR cost tracks the data, and safe re-runs via the `source_file` skip.

Where I'd take it next:

- **Skip EMR entirely on a re-run.** Today the skip happens *inside* the job — a re-run still starts Spark to find the files already loaded. Negligible at ~10 files/day, but a DynamoDB "processed files" ledger checked in the poller could skip them *before* EMR starts. Cheap correctness now; the optimization waits until scale pays for it.
- **Protect persistent S3 data** from stack deletion or replacement.
- **Quarantine** invalid or unmapped files instead of failing the group.
- **Data-quality checks** before the append.

## Summary

A serverless pipeline that batches a day's Parquet uploads into Apache Iceberg — SQS buffer, scheduled drain,
size-based bin-packing, one EMR job per group. Built with AWS SAM. The
[code is on GitHub](https://github.com/jabrennem/serverless-etl-s3-tables).
