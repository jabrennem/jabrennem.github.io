<h2 id="problem-and-solution">Part 1: Problem and solution</h2>

### The problem

Consider an upstream service that produces Parquet files and uploads them to S3. An analytics team needs 
the data ingested into managed Apache Iceberg tables in our data catalog in a timely manner. Uploads are infrequent 
and unpredictable, so the workload does not justify running resources.

That leaves three requirements for the pipeline. It should start processing when a file arrives, scale 
back down after the work finishes, and expose enough execution history to trace failures.

<div className="design-principles" aria-label="Pipeline requirements">
  <div>
    <p className="design-principle-number">01</p>
    <h4>Timely</h4>
    <p>Start processing as soon as a file arrives.</p>
  </div>
  <div>
    <p className="design-principle-number">02</p>
    <h4>Cost-effective</h4>
    <p>Avoid running compute between infrequent uploads.</p>
  </div>
  <div>
    <p className="design-principle-number">03</p>
    <h4>Observable</h4>
    <p>Make each execution and failure easy to trace.</p>
  </div>
</div>
### The solution

I split the solution into three layers so each concern can be designed and operated
independently:

- Storage
- Orchestration
- Compute

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

This architecture separates storage locations for the incoming data feed and the Iceberg table data referenced 
by downstream services and analytics teams. I store the source data in a general S3 bucket and use S3 Table Buckets 
for the AWS managed Iceberg tables. This allows for a clear separation between raw data and the catalog table 
data. Incoming files are uploaded under the feed/ prefix, giving the pipeline a clear boundary for identifying 
new data to ingest.

<StorageDiagram />

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

The orchestration layer is responsible for coordinating the ingestion process. The first step is to detect when new 
`feed/` objects are created. I configure the S3 bucket to send events to EventBridge. EventBridge rules can filter 
for events with the `feed/` prefix and then trigger a Step Functions state machine. Step Functions provides a visual 
execution history, built-in error handling, and support to run parallel tasks. Both EventBridge and Step Functions are
managed behind the scenes, so the entire orchestration layer is serverless and scales automatically.

<OrchestrationDiagram />

<div className="architecture-layer-heading">
  <span>03</span>
  <h4>Compute</h4>
</div>

The compute layer loads the incoming Parquet data into Iceberg. The current job reads each file as-is and writes 
its rows to the target table. I use Spark on EMR Serverless because it gives me control over the Spark configuration 
without keeping a cluster running between jobs. The Amazon S3 Tables integration exposes the table bucket through Glue's 
federated `s3tablescatalog`, allowing Spark to read from and write to the Iceberg tables.

There is an opportunity for collecting runtime statistics that downstream services can use for notifications or 
anomaly detection. The job writes these statistics as JSON under `runs/<execution-id>/stats/` in the source S3 
bucket. Using the execution ID connects the output to a specific Step Functions execution.

Before starting EMR Serverless, I use a Lambda function to validate the EventBridge payload and map each source file to an 
Iceberg table. This allows malformed or unmapped input to fail quickly and cheaply while keeping the Spark job focused on 
loading the data.

<h2 id="implementation">Part 2: Implementation</h2>

Part 1 described the architecture in three layers. This section shows how I implement each layer using
AWS SAM and application code. Security is applied within each layer rather than treated as a separate
component. The full source code is available in the
[GitHub repository](https://github.com/jabrennem/serverless-etl-s3-tables).

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

### Encrypting the data bucket

I use a customer-managed KMS key to encrypt objects in the data bucket because incoming files may contain
sensitive data such as PII or health information. Automatic rotation manages the key lifecycle, while an
S3 Bucket Key reduces calls to KMS and their associated cost.

```yaml
EncryptionKey:
  Type: AWS::KMS::Key
  Properties:
    Description: KMS key for S3 Bucket
    EnableKeyRotation: true
```

### Organizing the data bucket

I use the `DataBucket` for three types of objects:

- `feed/` stores the incoming data feed.
- `emr/` stores the runtime PySpark script.
- `runs/` stores runtime statistics.

The bucket publishes object events to EventBridge so the pipeline can react to `feed/` uploads. I also enable
versioning, block public access, send access logs to a separate bucket, and expire noncurrent versions after 30 days.
These settings provide recovery and audit trails without retaining old object versions indefinitely.

```yaml
DataBucket:
  Type: AWS::S3::Bucket
  Properties:
    NotificationConfiguration:
      EventBridgeConfiguration:
        EventBridgeEnabled: true
    BucketEncryption:
      ServerSideEncryptionConfiguration:
        - ServerSideEncryptionByDefault:
            SSEAlgorithm: aws:kms
            KMSMasterKeyID: !GetAtt EncryptionKey.Arn
          BucketKeyEnabled: true
    VersioningConfiguration:
      Status: Enabled
    PublicAccessBlockConfiguration:
      BlockPublicAcls: true
      BlockPublicPolicy: true
      IgnorePublicAcls: true
      RestrictPublicBuckets: true
    LoggingConfiguration:
      DestinationBucketName: !Ref LoggingBucketName
      LogFilePrefix: !Sub "${AWS::StackName}/"
    LifecycleConfiguration:
      Rules:
        - Id: ExpireNonCurrentVersions
          Status: Enabled
          NoncurrentVersionExpiration:
            NoncurrentDays: 30
```

The bucket policy denies requests that do not use HTTPS and grants the listed actions only to principals in the
configured AWS Organization.

```yaml
BucketPolicy:
  Type: AWS::S3::BucketPolicy
  Properties:
    Bucket: !Ref DataBucket
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: DenyInsecureTransport
          Effect: Deny
          Principal: "*"
          Action: "s3:*"
          Resource:
            - !GetAtt DataBucket.Arn
            - !Sub "${DataBucket.Arn}/*"
          Condition:
            Bool:
              aws:SecureTransport: "false"
        - Sid: AllowOrganizationAccess
          Effect: Allow
          Principal:
            AWS: "*"
          Action:
            - s3:GetObject
            - s3:PutObject
            - s3:DeleteObject
            - s3:ListBucket
            - s3:GetBucketLocation
          Resource:
            - !GetAtt DataBucket.Arn
            - !Sub "${DataBucket.Arn}/*"
          Condition:
            StringEquals:
              aws:PrincipalOrgID: !Ref PrincipalOrgId
```

### Defining the Iceberg destination

Amazon S3 Tables organizes Iceberg resources into three levels:

- Table bucket
- Namespace
- Table

I declare all three resources in the template so the table schema is version-controlled and the destination exists
before the first pipeline run. This keeps table-creation logic out of Spark.

```yaml
IcebergTableBucket:
  Type: AWS::S3Tables::TableBucket
  Properties:
    TableBucketName: !Ref TableBucketName

IcebergDefaultNamespace:
  Type: AWS::S3Tables::Namespace
  Properties:
    TableBucketARN: !GetAtt IcebergTableBucket.TableBucketARN
    Namespace: default

# test table for this service with a simple schema
IcebergTestDataTable:
  Type: AWS::S3Tables::Table
  DependsOn: IcebergDefaultNamespace
  Properties:
    TableBucketARN: !GetAtt IcebergTableBucket.TableBucketARN
    Namespace: default
    TableName: test_data
    OpenTableFormat: ICEBERG
    IcebergMetadata:
      IcebergSchema:
        SchemaFieldList:
          - Name: id
            Type: long
            Required: true
          - Name: name
            Type: string
            Required: false
          - Name: amount
            Type: double
            Required: false
```

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

### Coordinating independent loads

I keep the workflow logic in Step Functions instead of introducing additional Lambda functions. JSONata reshapes
the workflow payload inside the state definition, while the `.sync` integration pattern lets Step Functions wait
for each EMR Serverless job to finish.

A Map state iterates over the resolved source-to-table mappings, giving each input file an independent load path.
Each item starts `load_data.py` synchronously and passes the source object, catalog ID, namespace, target table,
and an execution-scoped statistics location. A failed item does not prevent the remaining items from running.

After the Map completes, a Choice state counts failed items. If any item has `status: "failed"`, the overall
execution fails. This preserves the completed loads while making partial failure visible in the Step Functions
console.

```json
"Check Table Results": {
  "Type": "Choice",
  "Choices": [{
    "Condition": "{% $count($states.input[status = 'failed']) > 0 %}",
    "Next": "Fail"
  }],
  "Default": "Succeed"
}
```

### Starting the workflow from S3

An EventBridge rule filters S3 `Object Created` events for keys under the `feed/` prefix and starts the state
machine. Its `InputTransformer` extracts the S3 key and shapes the input expected by the `ValidateInputFunction`.

```yaml
FeedUploadRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source:
        - aws.s3
      detail-type:
        - Object Created
      detail:
        bucket:
          name:
            - !Ref DataBucket
        object:
          key:
            - prefix: "feed/"
    Targets:
      - Id: LoadDataStateMachine
        Arn: !GetAtt StateMachine.Arn
        RoleArn: !GetAtt EventBridgeStateMachineRole.Arn
        InputTransformer:
          InputPathsMap:
            key: $.detail.object.key
          InputTemplate: |
            {
              "SourceFileTableNameMapping": [{"SourceFile": "<key>"}],
              "Event": {"source": "aws.s3", "detail-type": "Object Created", "key": "<key>"}
            }
```

I give the `EventBridgeStateMachineRole` only `states:StartExecution`, scoped to this state machine. This keeps the
event trigger from starting other workflows.

### Failing before EMR starts

I use a sub-second Lambda to validate the input before starting EMR Serverless. It checks the EventBridge payload
against a JSON Schema and maps each source file to an Iceberg table using regex patterns from `file_mapping.json`.

```yaml
ValidateInputFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: validate_input.handler
    CodeUri: lambda/validate_input/
```

```python
@logger.inject_lambda_context
def handler(event, context):
    validate(event=event, schema=INPUT_SCHEMA)

    for mapping in event["SourceFileTableNameMapping"]:
        if "TableName" not in mapping:
            table_name = resolve_table_name(
                mapping["SourceFile"], FILE_PATTERN_MAPPINGS
            )
            mapping["TableName"] = table_name

    return event
```

Table resolution checks patterns from longest to shortest so more specific matches take precedence. Adding an
ingestion target requires a new entry in `file_mapping.json` and a corresponding table resource in the SAM template.

```json
{
  "mappings": [
    {"tableName": "test_data", "filePattern": ".*/test-data\\.parquet$"}
  ]
}
```

### Scaling compute to zero

I configure an ARM64 Spark application on EMR release 7.8.0. Auto-start launches the application when a job arrives,
and a two-minute idle timeout stops it afterward. This leaves no EMR compute running between loads.

```yaml
EmrApp:
  Type: AWS::EMRServerless::Application
  Properties:
    ReleaseLabel: emr-7.8.0
    Architecture: ARM64
    Type: Spark
    AutoStartConfiguration:
      Enabled: true
    AutoStopConfiguration:
      Enabled: true
      IdleTimeoutMinutes: 2
```

The validation Lambda and EMR jobs use separate execution roles, allowing each role to be limited to the resources
it needs. When Lake Formation governs Data Catalog access, the EMR role also needs the grants shown in Part 3.

#### Loading Parquet into Iceberg

The Spark submission parameters configure the `s3tablesbucket` catalog to use the AWS Glue Iceberg REST endpoint,
sign requests with SigV4, and enable Iceberg's Spark extensions.

```bash
--conf spark.jars=/usr/share/aws/iceberg/lib/iceberg-spark3-runtime.jar
--conf spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions
--conf spark.sql.catalog.s3tablesbucket=org.apache.iceberg.spark.SparkCatalog
--conf spark.sql.catalog.s3tablesbucket.type=rest
--conf spark.sql.catalog.s3tablesbucket.uri=https://glue.${AWS::Region}.amazonaws.com/iceberg
--conf spark.sql.catalog.s3tablesbucket.warehouse=${GlueCatalogId}
--conf spark.sql.catalog.s3tablesbucket.rest.sigv4-enabled=true
--conf spark.sql.catalog.s3tablesbucket.rest.signing-name=glue
--conf spark.sql.catalog.s3tablesbucket.rest.signing-region=${AWS::Region}
```

The `load_data.py` script intentionally does not transform the source data. It reads Parquet, loads the rows into
Iceberg with `INSERT OVERWRITE`, and writes a statistics file for the state machine. I keep the catalog configuration
in `SparkSubmitParameters` so the script remains portable.

```python
def main(input_path, catalog_id, namespace, table_name, stats_s3_uri=""):
    iceberg_table = f"s3tablesbucket.{namespace}.{table_name}"

    spark = (
        SparkSession.builder
        .appName(f"S3TableBucket-Import-{table_name}")
        .getOrCreate()
    )

    df = spark.read.parquet(input_path)
    count = df.count()

    df.createOrReplaceTempView("source_data")
    spark.sql(f"INSERT OVERWRITE {iceberg_table} SELECT * FROM source_data")

    if stats_s3_uri:
        _write_stats_file(spark, stats_s3_uri, input_path, catalog_id,
                          namespace, table_name, count)
    spark.stop()
    return 0
```

The state machine reads the file written to `runs/<execution-id>/stats/<table>.json`, allowing structured metadata
to flow downstream without parsing Spark logs.

### Why the Lake Formation grants matter

Lake Formation is optional here. By default, Lake Formation uses **Use only IAM access
control** for new Data Catalog resources, so IAM policies control access. In the account
used for this deployment, Lake Formation permissions governed the catalog instead. In
that mode, IAM permissions alone are not enough for an EMR job to work with the catalog:
the EMR role must also be explicitly granted access to the S3 Tables catalog, its
`default` namespace, and the tables inside it.

If your account retains the IAM-only default, the PySpark upload is the only
post-deployment step needed; omit the Lake Formation grant commands.

The script applies the least privileges the job needs at each level:

- **Catalog** — `CREATE_DATABASE` and `DESCRIBE`, so the job can discover the catalog
  and create a database if needed.
- **Namespace** — `DESCRIBE`, `ALTER`, and `CREATE_TABLE`, so it can inspect and manage
  the `default` namespace.
- **Tables** — `SELECT`, `INSERT`, `DESCRIBE`, `ALTER`, and `DROP`, so it can read,
  write, and maintain the Iceberg tables created by the pipeline.

These grants are applied after deployment because the script derives both the deployed
EMR role and the account-specific S3 Tables catalog ID. Re-running it is safe: grants
that already exist are ignored.

The stack is tagged with an application identifier, which means all resources created by
CloudFormation inherit the tag. This integrates with AWS Cost Explorer, AWS Budgets, and
Cost Allocation Tags to track spend per pipeline — useful when you're running multiple
workloads in the same account and want to attribute costs back to individual services or

<h2 id="tradeoffs-and-next-steps">Part 4: Tradeoffs and next steps</h2>

This pipeline is deliberately simple - one file in, one table out. Moving toward production
means adding fail-safety to the pipeline.

The most immediate gap is **durability**. The DataBucket has no `DeletionPolicy`, so tearing
down the stack removes it. Setting `Retain` is a one-line fix but easy to forget.

Next is **throughput**. Right now each file triggers its own execution. That's fine at low
volume, but at dozens of files per minute the per-execution overhead adds up. Fronting the
EventBridge rule with an SQS queue and a small batching window lets multiple files share a
single state machine run, cutting Step Functions transitions and EMR cold starts.

Finally, there's the data schema itself. The table schema is defined in the SAM template,
which means schema changes go through version control and deploy — intentional, not accidental.
A lightweight data quality check before the write in EMR (validating column types and
rejecting unexpected schemas) would make the pipeline not just observable, but trustworthy.

### Summary

For data engineering teams, this is a practical way to turn an uploaded Parquet file
into a queryable Iceberg table without keeping infrastructure running between workloads.
New data is picked up as soon as it lands, each ingestion has a visible execution
history, and Spark compute spins up only when there is work to do. The result is a
pipeline that is timely, cost-effective, and observable, with clear places to extend it
as data volume, table count, and operational requirements grow.
