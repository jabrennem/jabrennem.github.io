<h2 id="problem-and-solution">Part 1: Problem and solution</h2>

### The problem

There is an external team that delivers a batch of small Parquet files to an S3 bucket every day. There are 
roughly 8 to 10 at a time with a few hundred to couple thousand records each. They usually arrive together,
but can also be delayed by hours. Each file is ingested into a specific Iceberg table in our catalog. Every 
once in a while, the same team also sends in the same batch much larger files with hundreds of millions of 
records that require some transformation logic.

I'm on a small team, so the design must require the least amount of resource management possible. When
something goes wrong I want to diagnose it quickly and retry the workflow so the data can be ingested again as 
quickly as possible. Cost must be minimal since the files are generally small. I don't want to pay for a 
heavyweight job unless it's for a file with millions of records.

That shapes four requirements. The pipeline should:
- consolidate a day's uploads into one run instead of reacting to each file
- scale to zero between batches
- spend compute in proportion to the data
- log enough history to trace a failure and safely re-run it.

### The solution

I split the solution into three layers

- Storage
- Orchestration
- Compute

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

This architecture separates storage for the incoming data feed and the Iceberg table data referenced by
downstream services and analytics teams. I store the source data in a general S3 bucket and use an S3 Table
Bucket for the AWS-managed Iceberg tables. This creates a clear boundary between raw data and catalog 
data. Incoming files from the external team land under the `feed/` prefix, which gives the pipeline a 
single place to watch, and in my demo, each file resolves by name to one of two Iceberg 
tables (`test_data` and `customers`).

<StorageDiagram />

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

The orchestration layer decides *when* to run and consolidates a window of uploads into a single 
execution for easy traceability. When the files are uploaded with a `feed/` prefix, it triggers 
an `S3 Object Created` event that is added to an SQS queue. The events wait in the queue until it's 
time to ingest. 

There is an EventBridge scheduler that invokes a Message Poller Lambda at set times daily to
check if there are messages in the queue. For example, if we poll at 9AM, we can launch 
the execution on the queued morning files to make sure they are ingested in the morning, and then
catch any delayed files with a 12PM check.

If the message poller finds files, it will assign a table name to the file based on its name 
and launch a single state machine execution with the full list of files from the queue. Step 
Functions provides a few tools that help with observability such as execution history, 
built-in error handling, and parallel task support.

<OrchestrationDiagram />

<div className="architecture-layer-heading">
  <span>03</span>
  <h4>Compute</h4>
</div>

The compute layer loads the Parquet files into Iceberg tables while trying to spend as little as 
possible. EMR Serverless is the expensive part of the pipeline, and each job is charged for start up 
time whether a job ingests a few kilobytes or gigabytes. Because of this, I chose to group small Parquet
files together using a size threshold. The larger Parquet files with millions of rows that require 
special transformations use their own EMR job. That way, the blast radius is isolated and doesn't affect 
the ingestion of other smaller files with simpler upload logic.

First, a Lambda validates the payload and performs the file grouping logic. Every file over 
a configurable size threshold gets its own job; all the small files share one. The state machine 
then runs one EMR Serverless Spark job per group and a single job can write to several tables 
at once.

Loads are idempotent by design. The Iceberg tables contain the original S3 location in a `source_file` 
column. Before appending data to a table, the job checks whether that file has already been ingested. If so,
it simply skips it. This way if a job fails, I can just rerun the state machine and do not risk data 
duplication. If any group fails, a Choice state fails the whole execution which keeps the completed executions 
green and brings attention to the failed runs in the console.

As a bonus, each job drops a per-group stats JSON under `runs/<execution-id>/stats/` for downstream analytics teams
or dashboards to use, so nobody has to parse Spark logs.

### Configure the deployment

Before deploying, I add the AWS Organization ID and the existing access logging bucket to the `parameter_overrides`
in `samconfig.yaml`:

```yaml
parameter_overrides:
  - PrincipalOrgId=o-xxxxxxxxxx      # your AWS Organization ID
  - LoggingBucketName=my-logging-bucket  # existing S3 bucket for access logs
```

### Build and deploy

With those values set, I specify an AWS profile and run the standard SAM build and deploy commands:

```bash
export AWS_PROFILE=profile_name
sam build
sam deploy
```

I run `sam build` to package the Lambda function and produce the transformed template used
for the deployment. This output is the first checkpoint that the application code and template 
built successfully.

### Prepare the test batch

`scripts/generate_test_data.py` writes a folder of small Parquet files split across both tables, with a couple
of deliberately larger files mixed in so the size threshold has something to isolate. For demo purposes,
the size threshold is set at 10KB. This threshold can be a lot more nuanced and reflective of the data in
production.

```bash
python scripts/generate_test_data.py --out test-batch --count 10
```

### Trigger the workflow

`trigger.sh` uploads the whole folder to the `feed/` prefix. Each object lands in the SQS queue; on its next
tick the scheduled Message Poller drains the queue and starts **one** state machine execution for the batch.
Since this is just a quick demo, the Lambda is checking the queue for messages every 2 minutes. This would
obviously be different in production.

```bash
./scripts/trigger.sh test-batch
# Uploads every *.parquet under test-batch/ to s3://<bucket>/feed/
```

### Follow the execution

The Message Poller resolves each file to its table and hands the state machine a flat list — each entry
carrying the resolved `TableName` and the object's `Size`. The Map state then runs one EMR job per 
group, so the ten uploaded files become a single execution with 3 jobs. One for the small files packed 
together, and each large file on its own.

In this demo, I'm using the same Pyspark script logic for the big files, but more complicated transformations
could be implemented here. The transformations could increase processing time at production scale, so having
the transformations in parallel means differents job finish around the same time and the small files are
uploaded way before.

### Reruns are safe

To prove the idempotency claim, I re-ran the same execution. The loader reads each file but skips the append
when that `source_file` is already in the table — so the second run committed nothing. Here's the driver log
from the batched small-file job on the rerun:

```text
Batch of 8 file(s) into catalog <ACCOUNT_ID>:s3tablescatalog/serverless-etl-table-bucket
Loading .../feed/customers-01-...-29403.parquet into s3tablesbucket.default.customers
  read 165 records
  skip .../feed/customers-01-...-29403.parquet -- already loaded into 's3tablesbucket.default.customers'
Loading .../feed/test-data-04-...-29834.parquet into s3tablesbucket.default.test_data
  read 145 records
  skip .../feed/test-data-04-...-29834.parquet -- already loaded into 's3tablesbucket.default.test_data'
  ... (all 8 files skipped)
```

All eight files skipped; the table row counts were unchanged. That's the whole safety net for a small team —
if a run half-fails, you just run it again.

### Did grouping actually save money?

The batch is 10 files (8 small, 2 big) run as **3 EMR jobs**. The billed resource use per job, from the EMR
console:

  <thead>
    <tr>
      <th>Job</th>
      <th>Files</th>
      <th>Billed vCPU-hours</th>
      <th>Billed memoryGB-hours</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Group 1 (small, batched)</td>
      <td>8</td>
      <td>0.287</td>
      <td>1.147</td>
    </tr>
    <tr>
      <td>Group 2 (big)</td>
      <td>1</td>
      <td>0.267</td>
      <td>1.067</td>
    </tr>
    <tr>
      <td>Group 3 (big)</td>
      <td>1</td>
      <td>0.267</td>
      <td>1.067</td>
    </tr>
    <tr>
      <td><strong>Grouped total</strong></td>
      <td>10</td>
      <td><strong>0.821</strong></td>
      <td><strong>3.281</strong></td>
    </tr>
  </tbody>
</table>

Every job billed about the same (~0.27 vCPU-hours) no matter what it loaded — that's the EMR Serverless per-job
floor. Running the 8 small files as separate jobs would pay that floor 8 more times: ~2.67 vCPU-hours vs 0.821
grouped, roughly **3× less billed compute** for the same data. And between batches the app auto-stops after two
idle minutes, so there's no idle compute at all.

<h2 id="tradeoffs-and-next-steps">Part 3: Tradeoffs and next steps</h2>

Where I'd take it next:

- **Skip EMR entirely on a re-run.** 
   - Today the skip happens *inside* the job. A re-run still starts Spark to 
     find the files already loaded. Negligible at ~10 files/day, but a DynamoDB 
     "processed files" ledger checked in Lambda could filter previously uploaded
     files *before* EMR starts.
- **Protect persistent S3 data** from stack deletion or replacement.
- **Data-quality checks** before the append to mask or validate column values.

## Summary

A serverless pipeline that batches daily Parquet uploads into Apache Iceberg using a SQS buffer, 
scheduled polling, size-based file grouping, one EMR job per group. Built with AWS SAM. The
[code is on GitHub](https://github.com/jabrennem/serverless-etl-s3-tables).
