<h2 id="problem-and-solution">Part 1: Problem and solution</h2>

### The problem

Consider an upstream service that produces Parquet files and uploads them to S3. An analytics team needs 
the data ingested into managed Apache Iceberg tables in our data catalog in a timely manner. Uploads are infrequent 
and unpredictable, so the workload does not justify persistent resources.

That leaves three requirements for the pipeline. It should start processing when a file arrives, scale 
back down after it finishes, and log enough execution history to trace failures.

<div className="design-principles" aria-label="Pipeline requirements">
  <div>
    <p className="design-principle-number">01</p>
    <h4>Timely</h4>
    <p>Start processing as soon as a file arrives.</p>
  </div>
  <div>
    <p className="design-principle-number">02</p>
    <h4>Cost-effective</h4>
    <p>Avoid running compute between infrequent uploads.</p>
  </div>
  <div>
    <p className="design-principle-number">03</p>
    <h4>Observable</h4>
    <p>Make each execution and failure easy to trace.</p>
  </div>
</div>
### The solution

I split the solution into three layers so each concern can be designed and operated
independently:

- Storage
- Orchestration
- Compute

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

This architecture separates storage locations for the incoming data feed and the Iceberg table data referenced 
by downstream services and analytics teams. I store the source data in a general S3 bucket and use S3 Table Buckets 
for the AWS managed Iceberg tables. This allows for a clear separation between raw data and the catalog table 
data. Incoming files are uploaded under the feed/ prefix, giving the pipeline a clear boundary for identifying 
new data to ingest.

<StorageDiagram />

<div className="architecture-layer-heading">
  <span>02</span>
  <h4>Orchestration</h4>
</div>

The orchestration layer is responsible for coordinating the ingestion process. The first step is to detect when new 
`feed/` objects are created. I configure the S3 bucket to send events to EventBridge. EventBridge rules can filter 
for events with the `feed/` prefix and then trigger a Step Functions state machine. Step Functions provides a visual 
execution history, built-in error handling, and support to run parallel tasks. Both EventBridge and Step Functions are
managed behind the scenes, so the entire orchestration layer is serverless and scales automatically.

<OrchestrationDiagram />

<div className="architecture-layer-heading">
  <span>03</span>
  <h4>Compute</h4>
</div>

The compute layer loads the incoming Parquet data into Iceberg. Each accepted Parquet file is treated as an additive
batch. The job reads its rows without applying business transformations and appends them to the target table. I use
Spark on EMR Serverless because it gives me control over the Spark configuration
without keeping a cluster running between jobs. The Amazon S3 Tables integration exposes the table bucket through Glue's 
federated `s3tablescatalog`, allowing Spark to read from and write to the Iceberg tables.

There is an opportunity for collecting runtime statistics that downstream services can use for notifications or 
anomaly detection. The job writes these statistics as JSON under `runs/<execution-id>/stats/` in the source S3 
bucket. Using the execution ID connects the output to a specific Step Functions execution.

Before starting EMR Serverless, I use a Lambda function to validate the EventBridge payload and map each source file to an 
Iceberg table. This allows malformed or unmapped input to fail quickly and cheaply while keeping the Spark job focused on 
loading the data.

<h2 id="implementation">Part 2: Implementation</h2>

Part 1 described the architecture in three layers. This section I want to dive more into how I implemented 
each layer using AWS SAM and Python. The full source code is available in the
[GitHub repository](https://github.com/jabrennem/serverless-etl-s3-tables).

<div className="architecture-layer-heading">
  <span>01</span>
  <h4>Storage</h4>
</div>

### Security: encryption and access

The bucket uses a customer-managed KMS key with automatic rotation for encryption at rest, giving me
CloudTrail visibility into every decrypt call and control over the key lifecycle. Access is scoped to the
AWS Organization rather than individual roles — new consumers onboard without policy changes, and enforces
all traffic through HTTPS.

### Bucket layout and lifecycle

The bucket is organized into three prefixes. `feed/` is where upstream services drop Parquet files — this
is the ingestion boundary that EventBridge watches. `emr/` holds the PySpark entrypoint, and `runs/`
collects statistics from each execution.

I enable versioning with a 30-day noncurrent expiration so I can recover from accidental overwrites without
storage growing indefinitely. The rest of the bucket configuration like access logging, public access 
blocks, etc. lives in the [full template on GitHub](https://github.com/jabrennem/serverless-etl-s3-tables).

### Iceberg destination: schema in version control

I define the S3 Table Bucket, namespace, and table in the SAM template so the destination exists before the
first pipeline run and the schema is reviewable in a pull request. This makes the demo simpler and keeps 
the DDL out of Spark. In production, schema evolution belongs in Iceberg-compatible tools like Spark or 
Athena. CloudFormation template changes force a table replacement and risks data loss.

```yaml
IcebergTestDataTable:
  Type: AWS::S3Tables::Table
  Properties:
    TableBucketARN: !GetAtt IcebergTableBucket.TableBucketARN
    Namespace: default
    TableName: test_data
    OpenTableFormat: ICEBERG
    IcebergMetadata:
      IcebergSchema:
        SchemaFieldList:
          - Name: id
            Type: long
            Required: true
          - Name: name
            Type: string
            Required: false
          - Name: amount
            Type: double
            Required: false
```

  <span>02</span>
  <h4>Orchestration</h4>
</div>

### Coordinating multiple ingestions

I keep the workflow logic in Step Functions rather than adding more Lambda functions. A Map state gives
each input file its own load path — if one file fails, the rest still complete. Each iteration starts the
EMR job synchronously and passes it the source object, target table, and a location for writing execution
statistics. Inside the state definitions, JSONata handles payload reshaping and the `.sync` integration
pattern blocks until each EMR job finishes.

After the Map completes, a Choice state counts failed items. If any item has `status: "failed"`, the overall
execution fails. This preserves the completed loads while making partial failure visible in the Step Functions
console.

```json
"Check Table Results": {
  "Type": "Choice",
  "Choices": [{
    "Condition": "{% $count($states.input[status = 'failed']) > 0 %}",
    "Next": "Fail"
  }],
  "Default": "Succeed"
}
```

### Starting the workflow from S3

An EventBridge rule filters S3 `Object Created` events for keys under the `feed/` prefix and starts the state
machine. Its `InputTransformer` extracts the S3 key and shapes the input expected by the `ValidateInputFunction`.

```yaml
FeedUploadRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source:
        - aws.s3
      detail-type:
        - Object Created
      detail:
        bucket:
          name:
            - !Ref DataBucket
        object:
          key:
            - prefix: "feed/"
    Targets:
      - Id: LoadDataStateMachine
        Arn: !GetAtt StateMachine.Arn
        RoleArn: !GetAtt EventBridgeStateMachineRole.Arn
        InputTransformer:
          InputPathsMap:
            key: $.detail.object.key
          InputTemplate: |
            {
              "SourceFileTableNameMapping": [{"SourceFile": "<key>"}],
              "Event": {"source": "aws.s3", "detail-type": "Object Created", "key": "<key>"}
            }
```

I give the `EventBridgeStateMachineRole` access to perform `states:StartExecution` only on this state 
machine. This keeps the event trigger from starting other workflows.

### Validate input before EMR starts

I use a sub-second Lambda to validate the input before starting EMR Serverless. It checks the EventBridge payload
against a JSON Schema and maps each source file to an Iceberg table using regex patterns from `file_mapping.json`.

```yaml
ValidateInputFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: validate_input.handler
    CodeUri: lambda/validate_input/
```

```python
@logger.inject_lambda_context
def handler(event, context):
    validate(event=event, schema=INPUT_SCHEMA)

    for mapping in event["SourceFileTableNameMapping"]:
        if "TableName" not in mapping:
            table_name = resolve_table_name(
                mapping["SourceFile"], FILE_PATTERN_MAPPINGS
            )
            mapping["TableName"] = table_name

    return event
```

Table resolution checks patterns from longest to shortest so more specific matches take precedence. Adding an
ingestion target requires a new entry in `file_mapping.json` and a corresponding table resource in the SAM template.

```json
{
  "mappings": [
    {"tableName": "test_data", "filePattern": ".*/test-data\\.parquet$"}
  ]
}
```

### Scaling compute to zero

I configure an ARM64 Spark application on EMR release 7.8.0. Auto-start launches the application when a job arrives,
and a two-minute idle timeout stops it afterward. This leaves no EMR compute running between loads.

```yaml
EmrApp:
  Type: AWS::EMRServerless::Application
  Properties:
    ReleaseLabel: emr-7.8.0
    Architecture: ARM64
    Type: Spark
    AutoStartConfiguration:
      Enabled: true
    AutoStopConfiguration:
      Enabled: true
      IdleTimeoutMinutes: 2
```

The validation Lambda and EMR jobs use separate roles scoped to their own resources. When Lake
Formation governs the Data Catalog, the EMR role will need Lake Formation grants
for catalog, namespace, and table-level access in addition to IAM. I apply these after deployment 
via a script that derives the role ARN and catalog ID from the stack outputs.

#### Loading Parquet into Iceberg

The Spark submission parameters register an s3tablesbucket catalog backed by Glue's Iceberg REST endpoint:

```bash
--conf spark.sql.catalog.s3tablesbucket=org.apache.iceberg.spark.SparkCatalog
--conf spark.sql.catalog.s3tablesbucket.type=rest
--conf spark.sql.catalog.s3tablesbucket.uri=https://glue.${AWS::Region}.amazonaws.com/iceberg
--conf spark.sql.catalog.s3tablesbucket.warehouse=${GlueCatalogId}
```

The full configuration is in the [state machine definition](https://github.com/jabrennem/serverless-etl-s3-tables).

The `load_data.py` script intentionally does not apply business transformations to the source data, but this
is an appropriate place to add, drop, or normalize columns. As of right now, it just reads the
Parquet rows, appends them to Iceberg, and writes a statistics file for the state machine. I keep 
the catalog configuration in `SparkSubmitParameters` so the script remains simple.

```python
def main(input_path, catalog_id, namespace, table_name, stats_s3_uri=""):
    iceberg_table = f"s3tablesbucket.{namespace}.{table_name}"

    spark = (
        SparkSession.builder
        .appName(f"S3TableBucket-Import-{table_name}")
        .getOrCreate()
    )

    df = spark.read.parquet(input_path)
    count = df.count()

    df.writeTo(iceberg_table).append()

    if stats_s3_uri:
        _write_stats_file(stats_s3_uri, input_path, catalog_id, namespace,
                          table_name, count)
    spark.stop()
    return 0
```

The state machine reads the file written to `runs/<execution-id>/stats/<table>.json`, allowing structured metadata
to flow downstream without parsing Spark logs.

### Complete the post-deployment setup

The post-deployment script uploads the PySpark entrypoint to S3. In accounts where Lake Formation governs Data
Catalog access, it also applies the grants required by the EMR role.


The script is idempotent, so it is safe to run more than once.

```bash
# Required only when Lake Formation permissions govern the catalog:

  --principal "DataLakePrincipalIdentifier=${EMR_ROLE_ARN}" \
  --resource '{"Catalog":{"Id":"<catalog-id>"}}' \
```

<h2 id="tradeoffs-and-next-steps">Part 4: Tradeoffs and next steps</h2>

This architecture is designed for infrequent, unpredictable uploads. The demo I put together proves the core 
workflow, but in production, it must also handle messier cases like duplicate events, higher traffic, 
and invalid raw data. 

If I were taking this to production with higher volume or less-trusted sources, these are the first things I'd address:
  - Protect persistent data in S3 from stack deletion or replacement.
  - Prevent data duplication by tracking which S3 object versions have already been ingested.
  - Batch higher volume ingestion with an SQS queue and process multiple files in the same EMR job.
  - Add data quality checks and inspect invalid files in a separate location

## Summary

Hope you enjoyed walking through this small project with me. It demonstrates an event-driven pipeline that 
loads parquet files from S3 into Iceberg using EventBridge, Step Functions, and EMR Serverless. I deployed it 
with AWS SAM and verified with a test run that cost roughly 2 cents. The design fits low-volume workloads and includes
future direction for production.
